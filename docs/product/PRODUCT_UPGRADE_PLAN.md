# Nolia 产品与技术升级方案

> 文档状态：目标版本实施基线
>
> 适用基线：Nolia 1.0.0，分支 `codex/nolia-upgrade`
>
> 交付方式：单一目标版本，一次性完成开发、集成、验收和发布
>
> 最近更新：2026-07-11

## 1. 文档目的

本文定义 Nolia 从 1.0.0 基线向下一阶段产品演进的共同方向，供产品设计、技术设计、开发、测试和发布决策使用。

本文不是版本发布说明。面向普通用户的版本迁移、备份和回退说明继续维护在 `docs/release/UPGRADE.md`。

本文重点回答以下问题：

1. Nolia 应服务哪类用户，解决什么核心问题。
2. 当前产品、UI/UX 和代码架构的主要优势与约束是什么。
3. 哪些能力应该优先建设，哪些能力暂时不做。
4. 技术架构如何支撑后续知识管理、AI 和插件能力。
5. 一次性交付范围、并行工作流、依赖、验收标准和风险是什么。

## 2. 执行摘要

Nolia 1.0.0 已具备完整桌面应用的基础能力：本地工作区、Markdown 编辑、全文检索、反向链接、历史版本、资源编辑、插件扩展和受控 AI。当前最主要的问题不是功能不足，而是功能尚未形成一条清晰、可重复的用户工作流，同时 renderer、插件运行时和工作区刷新链路已经接近继续扩张的风险边界。

建议将 Nolia 的产品定位从宽泛的“Markdown 知识工作站”收敛为：

> 本地优先、Markdown 原生、AI 操作可审计的项目知识工作台。

下一阶段不应优先复制 Notion 的云协作数据库，也不应直接追求 Obsidian 的插件数量。Nolia 应围绕以下闭环形成差异化：

```text
快速捕获 -> 清晰写作 -> 建立关联 -> 可靠检索 -> AI 辅助维护 -> 审查并落盘
```

升级工作以一个完整目标版本一次性交付。开发期间按架构安全、工作台、知识组织、AI、插件与质量保障等工作流并行推进，但不发布功能不完整的中间产品版本。所有范围必须在同一个集成分支完成联调，并共同通过发布门禁。

安全边界、数据契约和状态模型属于所有工作流的共同前置约束。并行开发不代表各模块可以使用临时接口或绕过最终架构。

## 3. 产品定位

### 3.1 目标用户

首要用户：

- 使用 Markdown 管理项目文档、设计记录、调研和知识库的开发者。
- 需要长期积累来源、笔记、报告和研究材料的研究人员与技术写作者。
- 需要在本地文件、Git 或同步盘中管理项目知识的个人和小型团队成员。
- 希望使用 AI 整理资料，但不接受 AI 静默修改文件或不透明上传上下文的用户。

暂不作为首要用户：

- 强依赖多人实时协作、评论、审批和复杂组织权限的大型团队。
- 主要需要在线数据库、表单、CRM 或项目管理看板的用户。
- 主要在移动端完成捕获和编辑的用户。

### 3.2 核心用户任务

用户选择 Nolia 时，应该能够稳定完成以下任务：

1. 在自己的文件夹中快速开始，不被专有格式锁定。
2. 以低干扰方式编写和维护 Markdown 文档。
3. 通过属性、标签、链接和搜索找回项目上下文。
4. 了解当前文档与其他文件之间的关系。
5. 让 AI 总结、改写、生成或整理内容，并清楚知道 AI 读取了什么、建议修改什么。
6. 在应用异常、外部编辑冲突或 AI 修改错误时恢复内容。

### 3.3 核心价值主张

- 文件归用户所有：正文始终是普通文件，索引和缓存可以重建。
- 知识可以连接：目录、属性、标签、链接和搜索组成统一知识模型。
- AI 可以信任：上下文透明、来源可见、写入需批准、修改可撤销。
- 专业但不过载：默认界面服务写作，复杂能力按需出现。

### 3.4 产品原则

1. Local-first 不是宣传语，而是数据模型和故障恢复原则。
2. Markdown 是事实来源，不建立必须依赖数据库才能读取的正文格式。
3. 默认路径必须简单，专业能力通过渐进披露提供。
4. 同一个用户目标只保留一个主要入口。
5. AI 不直接写入用户内容，所有写操作必须可审查、可拒绝、可撤销。
6. 外部插件按不可信代码处理，权限必须由运行时强制执行。
7. 派生数据必须有版本、重建、配额和损坏恢复策略。

## 4. 当前能力基线

### 4.1 已有产品能力

| 领域 | 当前能力 | 基线评价 |
| --- | --- | --- |
| 工作区 | 创建、打开、最近工作区、文件树、外部变更监听 | 基础完整，首次打开门槛偏高 |
| 编辑 | WYSIWYG、源码、分屏、GFM、公式、Mermaid、表格 | 能力丰富，复杂度较高 |
| 组织 | 文件夹、最近、收藏、标签索引、反向链接 | 功能存在但未形成组织闭环 |
| 检索 | SQLite FTS、路径和标签过滤、语义索引 | 后端较强，前端入口分散 |
| 历史 | 自动和手动快照、比较、恢复 | 可用，缺少保留与配额策略 |
| 资源 | JSON、文本、图片、PDF、音视频、压缩包 | 对技术型工作区有价值 |
| AI | 多 Provider、工具调用、RAG、proposal、审批、撤销 | 技术基础强，产品入口仍以聊天为主 |
| 插件 | Manifest、权限确认、命令、侧栏、查看器、编辑器 | 扩展面较广，安全隔离不足 |
| 国际化 | 多语言设置与覆盖测试 | 基础良好，文案模块过度集中 |
| 发布 | macOS、Windows、Linux 打包 | 已具备正式桌面产品基线 |

### 4.2 已有工程优势

- main、preload、renderer、shared 分层明确。
- IPC 请求集中定义，并使用 Zod 进行输入校验。
- BrowserWindow 开启 `sandbox`、`contextIsolation` 和 `webSecurity`。
- 工作区路径经过规范化和越界校验。
- 文本与二进制文件使用 hash 检测外部冲突，并通过临时文件替换实现原子保存。
- 用户正文与派生索引分离，数据库损坏时可以重建。
- AI 密钥与普通设置分离，优先使用系统安全存储。
- AI 写入已具备 proposal、审批、历史快照和撤销基础。
- 单元测试和 E2E 已覆盖 Markdown 边界、AI、插件、资源编辑和视觉布局等高风险区域。

## 5. 关键问题分析

### 5.1 产品问题

#### 5.1.1 功能很多，但核心循环不明显

当前活动栏包含最近、笔记、收藏、搜索、目录、命令、AI 和设置，用户可以完成很多操作，但进入工作区后缺少一个明确的起点。产品更像一个 Markdown IDE，而不是会主动帮助用户捕获、整理和找回知识的工作台。

#### 5.1.2 工作区准入门槛高

“打开工作区”只接受已经存在 `.nolia/workspace.json` 的目录。已有 Markdown 文件夹不能直接打开，需要先理解“创建”和“打开”的区别。这一行为比 Obsidian、VS Code 等同类工具更难理解。

#### 5.1.3 组织能力没有成为一等体验

标签、反向链接和最近文件已经进入索引，但它们分散在不同入口。缺少属性编辑、标签浏览、模板、Daily Note、Inbox 和关系视图，导致用户仍然主要依赖文件夹组织。

#### 5.1.4 AI 能力与用户感知不匹配

后端已经支持工具调用、任务、来源、proposal 和撤销，但用户主要看到聊天侧栏。真正有差异化的“可审计修改”和“多文件知识维护”没有被提升为核心交互。

### 5.2 UI/UX 问题

#### 5.2.1 导航入口重复

文件过滤、全文搜索、最近、收藏和命令面板都能用于“找到并打开内容”，但它们使用不同位置和交互模型。需要将“浏览”和“发现”重新分组。

#### 5.2.2 文档会话模型不清晰

renderer 保存多个 `openDocs`，但工作台没有稳定可见的文档标签、关闭和恢复模型。用户只能通过树或列表重新选择文件，内部状态与外部心智模型不一致。

#### 5.2.3 编辑器控制过度常驻

编辑、源码、分屏、目录、历史、收藏、搜索、刷新和 Markdown 工具栏同时存在。对熟练用户有效，但会削弱内容的视觉中心。默认编辑场景应更安静，模式和复杂工具按需出现。

#### 5.2.4 工作区空状态价值不足

欢迎页已经较完整，但工作区内未打开文档或刚完成初始化时缺少工作区主页。主区域的大面积空白没有承接新建、最近内容、模板和快速捕获。

#### 5.2.5 视觉语言偏工具容器

当前布局可靠、对比度稳定，但多个面板和设置项依赖边框容器。后续应减少页面级“卡片套卡片”，通过分区、间距、背景层级和内容排版建立结构。

### 5.3 架构问题

#### 5.3.1 Renderer 编排层过度集中

`src/renderer/App.tsx` 约 8700 行，承担工作区生命周期、文档会话、资源编辑、历史、搜索、AI、插件、布局和弹窗。其状态和副作用相互依赖，已经不适合继续直接叠加功能。

`src/renderer/components/WysiwygEditor.tsx`、`src/renderer/styles/global.css`、`src/shared/i18n.ts` 也已经超过适合单文件维护的规模。

#### 5.3.2 编辑链路存在重复计算

源码变化会立即跨 IPC 请求完整 Markdown 解析。预览 effect 通过拼接所有打开文档的完整正文检测变化。长文档、多文档和快速输入场景可能产生排队解析、无效结果和主线程压力。

#### 5.3.3 文件树刷新是全量递归

当前文件树使用递归 `readdir` 和串行 `stat` 构建。保存、刷新和 watcher 事件可能重新获取整棵树。随着工作区文件量增长，该模型会同时影响响应速度、文件描述符和电量消耗。

#### 5.3.4 派生数据库写放大

工作区数据库使用 `sql.js`。持久化时需要导出完整数据库文件。当前规模可接受，但语义索引增长后需要通过基准判断是否继续使用，并应先引入存储接口隔离具体实现。

#### 5.3.5 历史快照没有生命周期

自动保存可以为每次有效内容变化创建快照，但没有按数量、时间和空间配额清理的策略。长期工作区可能持续增长。

### 5.4 安全问题

#### 5.4.1 插件权限不是强隔离

外部插件通过动态 `import()` 运行在主 renderer 的同一 JavaScript 上下文。虽然宿主提供了带权限校验的 `context.api`，插件仍可能直接访问页面 DOM 和 `window.nolia`，从而绕过插件 API 的权限约束。

因此，在完成隔离前，以下表述不能作为安全承诺：

- “插件只能使用 `context.api`”。
- “未授予的工作区权限无法被插件访问”。
- “插件网络访问由 manifest 权限完整控制”。

#### 5.4.2 插件网络权限与 CSP 不一致

插件网络请求当前由 renderer 中的 `fetch` 执行，而 CSP 的 `connect-src` 只允许应用协议和开发服务器地址。即使用户授予 `network:request:<host>`，请求也可能被 CSP 拦截。网络代理应迁移到 main process，并在 main 中执行 host allowlist 校验。

### 5.5 质量问题

当前检查结果：

- `npm run typecheck`：通过。
- `npm run lint`：通过。
- `npm run build`：通过。
- 单元测试：121 个断言通过，但 Vitest 因 9 个 `EMFILE: too many open files, watch` 未处理错误以失败状态退出。

已确认部分测试在重新打开工作区后没有关闭 watcher。断言通过不能替代进程无泄漏退出，该问题属于目标版本发布阻塞项。

生产构建基线：

- renderer 主入口约 191 KB，已经完成有效的首屏拆分。
- WYSIWYG chunk 约 2.40 MB。
- Mermaid vendor chunk 约 2.72 MB。
- Source editor chunk 约 664 KB。
- 主 CSS 约 101 KB。

大 chunk 已延迟加载，但仍需设置加载时延和内存预算。

## 6. 竞品参考与取舍

| 产品 | 值得吸收 | 不应直接复制 |
| --- | --- | --- |
| Obsidian | 本地文件、属性、双链、局部关系图、模板、Daily Note | 设置复杂度、插件依赖和功能碎片化 |
| Typora | 编辑与预览融合、低干扰写作、快捷格式操作 | 只关注单文件的产品边界 |
| Logseq | Journal、快速捕获、任务聚合、查询思想 | 强制大纲和块引用数据模型 |
| Notion | 工作区主页、模板、优质空状态、统一搜索 | 云数据库、实时协作和块格式锁定 |
| Craft/Bear | 内容排版、渐进披露、标签体验 | 封闭同步和平台绑定 |
| VS Code | 命令体系、会话恢复、扩展宿主、工作区模型 | IDE 式功能密度和开发工具心智 |

明确取舍：

- 做局部关系图，不优先做全局大型图谱。
- 做 Markdown frontmatter 属性，不做 Notion 式任意数据库。
- 做 Daily Note 和 Inbox，不强制所有内容使用 Journal。
- 做受控 AI 任务，不做默认自动改写整个工作区。
- 做隔离的本地插件，不在 API 稳定前建设插件市场。
- 优先兼容 Git 和同步文件夹，不在产品验证前自建同步云。

## 7. 目标信息架构

### 7.1 一级导航

建议将左侧主导航收敛为三个主要入口：

1. 文件：文件树、文件过滤、新建、移动和资源。
2. 发现：最近、收藏、搜索、标签、智能集合和关系入口。
3. AI：对话、任务、待审批修改和历史运行。

目录、历史和文档详情属于当前文档上下文，放入右侧检查器；设置与命令面板保留为全局工具。

### 7.2 工作区主页

没有活动文档时，主区域显示工作区主页，而不是空白编辑器。主页至少包括：

- 快速新建笔记。
- 打开今日笔记。
- 快速捕获到 Inbox。
- 最近编辑和收藏。
- 待审批 AI 修改。
- 索引、同步目录冲突和工作区健康状态。

主页不应成为营销页面，也不需要大尺寸装饰插画。

### 7.3 文档区域

- 提供可见的文档标签或最近文档栈。
- 显示未保存状态，关闭时根据自动保存和冲突状态决定是否确认。
- 支持恢复上次会话，但只恢复有限数量的活动文档。
- 默认使用编辑模式；源码和分屏作为专业模式保留。
- Markdown 工具栏根据模式、选区和窗口宽度自适应。

### 7.4 右侧检查器

右侧检查器统一承载：

- 目录。
- 属性与标签。
- 链接关系。
- 历史版本。
- 诊断与冲突。

检查器可以折叠，并记忆每个工作区的最后状态。不要在一级导航重复放置目录入口。

## 8. 核心功能升级

### 8.1 工作区与导入

- “打开文件夹”允许选择普通目录。
- 检测到非 Nolia 目录时展示初始化说明，确认后只创建 `.nolia/` 派生目录，不修改现有正文。
- 初始化前展示可索引文件数量、忽略规则和是否可写。
- 支持从其他 Markdown 工具导入设置，但不搬运或复制正文文件。
- 增加工作区健康检查：路径权限、索引状态、历史空间、损坏数据库备份和同步冲突提示。

### 8.2 捕获、模板与日记

- 支持配置 Inbox 路径。
- 提供全局快速捕获命令，可以只输入标题或一段正文。
- Daily Note 使用可配置路径和文件名模板。
- 模板本身保存为 Markdown 文件，支持基础变量，例如日期、时间、标题和当前工作区。
- 模板渲染不执行任意 JavaScript。

### 8.3 属性和标签

- 在右侧检查器中提供 frontmatter 属性编辑器。
- 首期支持字符串、数字、布尔、日期、字符串列表和标签。
- 保留未知 YAML 字段，不因可视化编辑丢失格式外的数据。
- 标签支持浏览、自动补全、重命名预览和使用数量。
- 属性写回必须复用原子保存、冲突检测和历史快照。

### 8.4 链接与关系

- 输入 `[[` 时提供文件和标题自动补全。
- 文档检查器同时展示出链、反向链接和未链接提及。
- 重命名文件时计算引用更新预览，用户确认后批量执行。
- 首期实现以当前文档为中心的局部关系图，限制节点数量并支持跳转。
- 全局图谱放在后续评估，不作为本次目标版本的发布阻塞项。

### 8.5 统一搜索

统一搜索结果来源：

- 标题、正文和路径。
- 标签和 frontmatter 属性。
- 最近与收藏。
- 任务项。
- 语义检索结果。

搜索 UI 要求：

- 同一输入框支持自然关键词和显式筛选器。
- 结果显示命中类型、路径、摘要和更新时间。
- 支持键盘选择、预览和打开。
- 支持保存搜索为智能集合。
- 语义结果必须标记来源，不与精确匹配混淆。

### 8.6 AI 工作流

AI 从“聊天功能”升级为以下三个入口：

1. 内联动作：改写选区、解释、翻译、提取任务和继续写作。
2. 文档助手：总结当前文档、生成结构、发现缺失链接、检查一致性。
3. 工作区任务：整理 Inbox、生成项目报告、批量补充属性、提出文件移动方案。

所有入口共享以下规则：

- 运行前展示将使用的上下文范围。
- 结果引用具体文件和片段。
- 写操作生成 proposal，不直接落盘。
- 多文件 proposal 使用逐操作 diff，支持部分接受。
- 应用 proposal 前创建事务记录和必要快照。
- 任务中心展示运行状态、工具步骤、待审批项、失败原因和撤销入口。
- Provider、模型和外发数据范围在界面中可见。

## 9. 目标技术架构

### 9.1 Renderer feature 边界

建议的目标目录：

```text
src/renderer/
  app/
    AppShell.tsx
    routing/
    session/
  features/
    workspace/
    documents/
    explorer/
    discovery/
    history/
    settings/
    ai/
    plugins/
  editors/
    markdown-wysiwyg/
    markdown-source/
    text-resource/
  components/
  styles/
```

拆分原则：

- `AppShell` 只负责布局、顶层错误边界和 feature 装配。
- 工作区、文档、AI 和插件各自拥有状态、命令和副作用。
- 跨 feature 通信通过有类型的 command/event 或明确 service 完成。
- 服务端数据与 UI 偏好分开，不把所有状态都放入一个全局 store。
- 迁移过程保持现有行为，每次只移动一个垂直切片。

### 9.2 建议状态模型

```text
WorkspaceSession
  workspaceInfo
  indexStatus
  treeSnapshot
  health

DocumentSession
  tabs
  activeDocumentId
  drafts
  saveState
  conflicts

DiscoveryState
  query
  filters
  results
  savedSearches

AiSession
  activeConversation
  runningTasks
  approvals
  proposals
```

文档正文不能在多个互不一致的 state 和 ref 中各自维护副本。需要为 source、WYSIWYG draft、disk revision 和 parsed result 定义明确版本号。

### 9.3 编辑和解析管线

- renderer 立即更新编辑器本地状态。
- 解析请求按文档 debounce，并携带 revision。
- Markdown AST 解析和 HTML 渲染迁移到 Web Worker 或 renderer worker。
- main process 只处理需要文件系统或数据库权限的操作。
- 旧 revision 的结果直接丢弃，不继续更新 UI。
- Mermaid 只在当前文档实际包含 Mermaid fence 时加载。
- 大文档设置降级策略，例如延迟目录、关系和语义更新。

### 9.4 工作区索引和文件树

- watcher 事件聚合为批次，并区分 create、change、delete、move。
- main process 维护文件树快照，通过增量 patch 通知 renderer。
- UI 展开的目录按需加载或虚拟化，避免每次传输完整树。
- 索引任务使用有界并发，不串行处理所有文件，也不无限并发。
- 文件 hash、mtime 和 size 未变化时跳过正文读取。
- 全量 rebuild 与增量索引使用相同的状态机和诊断事件。

### 9.5 数据存储

先定义 `WorkspaceRepository` 接口，隔离以下能力：

- 文件元数据。
- 文档索引。
- 链接和标签。
- 最近记录。
- 历史元数据。
- 语义 chunk 和 embedding。

本次目标版本不直接迁移数据库。完成 1 万、5 万文件和语义索引压力测试后，再决定继续优化 `sql.js` 或迁移原生 SQLite。迁移必须考虑 Electron 跨平台打包和 native module rebuild 成本。

### 9.6 插件隔离

推荐架构：

```text
Plugin code
  -> isolated iframe / dedicated process
  -> MessagePort RPC
  -> Plugin capability broker
  -> validated main-process service
  -> workspace / network / clipboard
```

要求：

- 插件上下文中不存在 `window.nolia`。
- 每个请求包含宿主生成的 plugin identity，不能由插件自行声明。
- main process 根据 manifest、用户授权和请求目标再次校验权限。
- 网络请求由 main 执行，并校验协议、host、重定向和响应体上限。
- UI 贡献使用声明式描述或隔离 iframe，不允许插件任意修改宿主 DOM。
- 插件崩溃、超时和资源占用不会阻塞主 renderer。
- API 版本升级提供兼容层和明确废弃周期。

## 10. 一次性交付模型

### 10.1 目标版本范围

以下能力必须在同一个目标版本中完整交付：

- 插件强隔离、main 侧权限校验和网络代理。
- watcher 生命周期修复、历史配额和性能基准。
- renderer feature 化、文档 revision 模型和增量文件树。
- 普通目录初始化、工作区主页和文档会话恢复。
- 文件、发现、AI 三个一级入口和统一右侧检查器。
- Inbox、Daily Note、模板、属性和标签。
- 链接补全、出链、反向链接、未链接提及和局部关系图。
- 统一搜索、保存搜索和全文/语义混合检索。
- AI 内联动作、任务中心、多文件 diff、部分接受和事务撤销。
- Plugin API v3、兼容层、示例插件和开发文档。
- 完整迁移、回退、性能、无障碍、跨平台和发布验证。

### 10.2 并行工作流

开发按工作流并行组织，而不是按功能阶段依次发布：

| 工作流 | 主要责任 | 必须产物 |
| --- | --- | --- |
| 架构与安全 | feature 边界、IPC、插件隔离、权限、迁移 | 最终接口、威胁模型、越权测试 |
| 工作区与数据 | 初始化、文件树、索引、历史、属性、链接 | repository、增量事件、迁移工具 |
| 编辑器与会话 | 标签、revision、保存、解析、预览 | 文档状态机、worker、冲突恢复 |
| 产品工作台 | 首页、导航、发现、搜索、检查器 | 完整主流程和全状态 UI |
| AI 工作台 | 内联动作、任务、proposal、diff、撤销 | 可恢复任务和事务链路 |
| 插件生态 | API v3、隔离 UI、SDK、兼容层 | 示例插件、兼容测试、指南 |
| 质量与发布 | 自动化、性能、无障碍、三平台打包 | 发布报告和一次性上线清单 |

各工作流可以在独立 feature branch 开发，但必须持续合入同一集成分支。任何临时 mock 契约在发布前都必须替换为最终 shared schema。

### 10.3 依赖关系

一次性交付不取消工程依赖。必须先冻结以下共同契约，其他工作流才能稳定并行：

1. Workspace、Document、Search、AI Task 和 Plugin RPC 的领域模型。
2. shared IPC schema、事件 envelope 和错误码。
3. 文档 revision、磁盘 hash、draft 和 parsed result 的一致性规则。
4. `.nolia` schema 版本、迁移和重建策略。
5. UI token、布局断点和全局命令 ID。

依赖完成只代表内部开发可以继续，不形成对外发布节点。

### 10.4 唯一发布门禁

目标版本只有一个发布门禁。以下条件必须同时满足：

- 所有目标范围已经落地，不存在隐藏开关后的半成品主流程。
- `typecheck`、`lint`、unit、E2E、build 和三平台打包全部通过。
- 测试进程零 unhandled rejection、open handle 和资源泄漏。
- 未授权插件无法访问工作区、剪贴板或网络能力。
- 普通目录初始化、旧工作区升级和失败回退均通过验证。
- 属性编辑、文件重命名和 AI 多文件事务不会造成静默数据丢失。
- 1 万文件和 10 万字文档达到性能预算。
- 所有核心页面通过最小窗口、键盘、屏幕阅读器和视觉回归验收。
- 用户手册、插件指南、架构文档、隐私说明和发布说明全部同步。

## 11. 本次交付边界

### 11.1 必须交付

- 第 10.1 节列出的全部目标版本范围。
- 技术设计文档定义的架构、安全、数据和质量约束。
- UI/UX 规格定义的页面、交互、状态和无障碍要求。

### 11.2 明确不纳入本次交付

- 插件市场。
- 自建云同步。
- 多人实时协作。
- Notion 式数据库。
- Canvas 和白板。
- 移动端原生应用。

全局知识图谱不作为独立页面交付，但当前文档的局部关系图属于本次范围。

## 12. 性能与质量指标

### 12.1 产品指标

- 新用户 60 秒内完成工作区初始化和第一篇笔记创建。
- 常用命令最多通过一次快捷键和一次确认完成。
- 最近打开、搜索和链接跳转形成稳定的内容找回路径。
- AI proposal 的接受、部分接受、拒绝和撤销均可统计成功率。

产品统计默认应保存在本地。任何遥测必须单独征得同意，并在隐私声明中说明字段和用途。

### 12.2 性能指标

| 场景 | 目标 |
| --- | --- |
| 冷启动到可交互 | 常用设备 P95 小于 2 秒 |
| 输入反馈 | 主线程阻塞小于 16 ms |
| 分屏预览更新 | P95 小于 250 ms |
| 1 万文件全文搜索 | P95 小于 150 ms |
| 单文件外部变化可见 | P95 小于 500 ms |
| AI 流式首段响应 | 排除 Provider 网络后小于 300 ms |
| 工作区关闭 | watcher、索引和数据库在 2 秒内完成或安全取消 |

### 12.3 质量门禁

目标版本必须通过：

```sh
npm run typecheck
npm run lint
npm test
npm run e2e
npm run build
```

额外要求：

- 测试进程不能包含 unhandled rejection、open handle 或资源泄漏。
- 核心 UI 需要覆盖 1320x860、1100x760、900x700 和应用最小窗口。
- 影响 main、preload 或 IPC 的改动必须包含输入校验和越权测试。
- 影响 Markdown 转换的改动必须覆盖双向转换与复杂语法回归。
- 影响工作区数据的改动必须包含升级、回退、损坏和中断场景。

## 13. 数据兼容与迁移原则

- 不迁移或重写用户 Markdown 正文，除非用户主动确认具体操作。
- `.nolia` schema 必须有显式版本。
- 派生数据库升级失败时优先备份旧库并重建，不能阻止用户读取正文。
- 设置迁移必须保留未知字段或提供清晰废弃策略。
- 插件 API 升级至少保留一个主版本兼容窗口。
- AI 任务、审批和事务记录需要定义可恢复状态，不能只依赖 renderer 内存。

## 14. 风险登记

| 风险 | 影响 | 应对 |
| --- | --- | --- |
| 大规模拆分造成编辑回归 | 高 | 垂直切片迁移，行为测试先行 |
| 插件隔离破坏现有示例 | 高 | 提供兼容桥和迁移指南 |
| 原生 SQLite 增加打包复杂度 | 高 | 先做 repository 抽象和基准，不提前迁移 |
| 属性编辑破坏 YAML | 高 | AST/CST 级 YAML 修改，保留未知字段和格式 |
| AI 多文件操作部分失败 | 高 | 事务日志、预检查、逐操作状态和补偿恢复 |
| 文件树虚拟化影响拖拽 | 中 | 保留键盘移动和对话框移动作为可靠路径 |
| 导航重构影响老用户 | 中 | 快捷键保持兼容，提供一次性变更说明 |
| 功能范围持续膨胀 | 高 | 以第 10.1 和 11.2 节锁定范围，新增需求必须替换等量范围 |

## 15. 决策与评审机制

各并行工作流开始实现前应产出：

1. 用户流程和界面原型。
2. 技术设计和数据契约。
3. 迁移与兼容说明。
4. 测试计划和性能预算。
5. 可独立发布的 issue 列表。

涉及以下内容必须单独评审：

- 用户文件批量修改。
- IPC 和 preload API 扩展。
- 插件权限或网络能力。
- 数据库 schema 和设置迁移。
- AI 上下文、工具权限和写入行为。
- Electron、React、TipTap、CodeMirror、AI SDK 等核心依赖升级。

## 16. 完成定义

一个升级项只有同时满足以下条件才算完成：

- 用户目标和非目标已经明确。
- 交互具备加载、空、错误、冲突和取消状态。
- main 侧完成输入与权限校验。
- 数据升级和失败恢复路径可验证。
- 单元、集成或 E2E 覆盖与风险匹配。
- 性能没有突破所属场景预算。
- 用户手册、架构地图或插件指南已按影响更新。
- 发布说明包含用户可感知变化和已知限制。

## 17. 一次性交付执行要求

所有工作流从同一组冻结契约开始，并持续集成：

1. 建立目标版本集成分支、契约变更规则和每日构建。
2. 同时启动插件隔离、repository、文档状态机、设计系统和测试基础设施工作。
3. 契约冻结后并行开发工作区、编辑器、发现、AI 和插件功能。
4. 每个垂直功能合入时必须包含最终 UI、错误状态、数据迁移和自动化测试，不接受只合后端或只合静态页面。
5. 持续运行大工作区、长文档、AI 事务和插件越权测试，不能留到发布前集中处理。
6. 所有功能完成后进入统一硬化周期，只修复阻塞缺陷、性能、兼容和文档问题，不再增加范围。
7. 最终只发布一次，发布内容必须满足第 10.4 节全部门禁。

内部依赖可以决定代码合入顺序，但不改变一次性完成、一次性验收和一次性发布的产品要求。
